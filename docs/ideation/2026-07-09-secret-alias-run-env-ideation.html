Ideation: Secret Alias Mapping for keyblind run --env

Focus: allow HELLO to be injected as WORLD
Mode: repo-grounded
Grounding Axes Ranked Ideas Rejected

Grounding Context

Codebase context. Keyblind is a Node.js TypeScript ESM CLI/MCP project. Runtime secret injection for child processes is concentrated in src/run.ts, while src/cli.ts is already a thin adapter that passes listSecrets() and resolveSecret into runCommandWithSecrets. The current run path injects every listed secret under its stored name.

Existing run behavior. parseRunArgs only understands --allow-unsafe and --. buildRunEnvironment copies the base environment, resolves each secret name, skips names or values containing null bytes, injects env[name] = value, and records non-empty injected values for leak redaction. Tests in tests/run.test.ts directly cover argument parsing, environment preparation, unsafe preflight, redaction, and child-process outcomes.

Security posture. The recent run-guard plan says keyblind run should remain guarded by default, exact injected values should be the leak-detection authority, and src/run.ts should keep the policy surface behind a focused helper. It also says sandbox fakes should not be treated as leaks unless they were actually injected for the current run.

Sandbox boundary. src/sandbox.ts owns .env file replacement and internal backup records using __keyblind_sandbox_backup__*. That is a different lifecycle from process-time env injection. Alias support should avoid making sandbox backups or deterministic fakes part of user-facing alias semantics.

Past learnings. The architecture simplification learning argues for deep modules and deletion-first discipline: add a capability at the existing strong seam instead of creating a new broad product surface. The Node compatibility learning is only tangential; it reinforces keeping dependency and tool changes minimal.

External context. 1Password's op run is useful prior art: it passes secrets as environment variables to a subprocess, can load references from env files, defines precedence among sources, and masks printed secrets by default. That supports a process-time mapping design, not a persisted alias registry. Source: 1Password CLI run reference.

Topic Axes

  • CLI contract: how users express aliases without confusing child command arguments.
  • Injection semantics: which secrets are resolved, under which env names, and with what precedence.
  • Safety and auditability: how aliases interact with leak redaction, blocked commands, audit log names, and null-byte filtering.
  • Backend and product boundary: whether aliases work only for local vault secrets or across configured backends.
  • Docs and tests: how the feature becomes discoverable and regression-resistant.

Ranked Ideas

  1. Run-only explicit env map: --env HELLO:WORLD
  2. Selection mode: --env NAME plus --env SOURCE:TARGET
  3. First-class parser type for secret env specs
  4. Alias-aware redaction and audit labeling
  5. Backend-aware run injection while adding aliases
  6. Documented precedence model matching env tooling expectations

1. Run-only explicit env map: --env HELLO:WORLD

Axis: CLI contract Confidence: 90% Complexity: Low

Description: Add a repeatable --env SOURCE:TARGET flag to keyblind run. For each spec, resolve secret SOURCE and inject the value as child environment variable TARGET. This directly matches the requested workflow: store HELLO, run with --env HELLO:WORLD, and the child process sees WORLD.

Basis: direct: src/run.ts already centralizes env construction in buildRunEnvironment, which currently assigns env[name] = value; the requested change is the smallest extension of that seam.

Rationale: This gives the user the exact alias behavior without creating persistent alias state, modifying sandbox backup records, or weakening the guarded run path.

Downsides: Needs careful parsing so --env is consumed only before the child command separator. It also needs clear validation for env-var names and missing target names.

2. Selection mode: --env NAME plus --env SOURCE:TARGET

Axis: Injection semantics Confidence: 84% Complexity: Medium

Description: Make --env an explicit injection selector. With no --env flags, preserve today's behavior and inject all secrets. Once any --env flag appears, inject only the requested specs: --env HELLO injects HELLO as itself, and --env HELLO:WORLD injects it as WORLD.

Basis: reasoned: aliasing is often used to fit an app's expected variable names. If the user asks for HELLO:WORLD, also injecting every other vault secret is unnecessary exposure and conflicts with Keyblind's safety posture.

Rationale: This turns aliases into a smaller blast-radius feature instead of a mere duplicate-name convenience. It also gives users a natural way to run a command with only the secrets it needs.

Downsides: It is a semantic branch: keyblind run --env X -- cmd differs from keyblind run -- cmd. The docs and tests must make that intentional.

3. First-class parser type for secret env specs

Axis: Docs and tests Confidence: 88% Complexity: Low

Description: Add a small type such as RunSecretSpec { sourceName, targetName } and parse flags into that structure before environment construction. Keep parsing, validation, env-building, and command spawning separately testable in src/run.ts.

Basis: direct: the existing tests already isolate parseRunArgs and buildRunEnvironment. The prior guard plan's technical decision KTD1 says run behavior should stay behind a focused runtime helper instead of swelling src/cli.ts.

Rationale: This keeps the feature deep in the existing module and prevents ad hoc string logic from spreading through the CLI branch. It also makes edge cases cheap to test: repeated aliases, malformed specs, separator handling, null bytes, and duplicate targets.

Downsides: Slightly more code than patching the existing secretNames: string[] loop, but it pays for itself as soon as alias validation and explicit selection are added.

4. Alias-aware redaction and audit labeling

Axis: Safety and auditability Confidence: 78% Complexity: Medium

Description: Keep redaction keyed to actual resolved values, but make diagnostics talk in terms of the injected env target when useful. For example, if HELLO is injected as WORLD and the child leaks the value, the terminal should still redact the value and can report that an injected value was exposed through the current run without printing either plaintext or expanding the audit surface.

Basis: direct: src/run.ts currently records leakValues from resolved secret values, not from names. The guard plan says exact injected values are the detection authority.

Rationale: Alias support must not accidentally downgrade the leak guard. This design preserves the current security invariant: every non-empty resolved value injected under any name is included in the redactor set once.

Downsides: Name-level diagnostics can become sensitive. Keep terminal wording generic unless a future product decision allows showing alias names in guarded-run metadata.

5. Backend-aware run injection while adding aliases

Axis: Backend and product boundary Confidence: 70% Complexity: Medium

Description: Use the alias implementation to revisit one adjacent inconsistency: MCP resolution uses the configured backend, while the current CLI run branch passes local listSecrets() and resolveSecret. A clean alias design can accept a generic resolver and, when no explicit specs are passed, continue existing local behavior until backend-run parity is deliberately planned.

Basis: direct: src/server.ts resolves through getBackend() for MCP, while src/cli.ts run currently passes vault-local functions. The project claims backend support in README and CLI help.

Rationale: This is the best follow-up pressure revealed by the alias request. Aliases are a process-time resolution concern, so they should not bake in assumptions that make backend parity harder later.

Downsides: Solving backend parity inside this feature could overrun scope. The first implementation can keep the resolver interface flexible and leave full backend-run parity as a named follow-up.

6. Documented precedence model matching env tooling expectations

Axis: CLI contract Confidence: 76% Complexity: Low

Description: Define precedence explicitly: base process env is copied first, Keyblind injected specs override it, and when multiple specs target the same env var, the last --env wins or the command fails fast. The better first version is fail-fast on duplicate targets unless a stronger compatibility reason appears.

Basis: external: 1Password documents source precedence for its run command because env injection from multiple places otherwise becomes ambiguous. Keyblind should make the smaller equivalent decision up front.

Rationale: Env aliasing creates collisions by design. A clear rule prevents invisible surprises where one alias silently shadows another or overwrites an existing shell variable.

Downsides: Fail-fast duplicate-target validation is stricter than some env tools. If users expect "last wins", they may need one docs sentence explaining why Keyblind is stricter for secret injection.
